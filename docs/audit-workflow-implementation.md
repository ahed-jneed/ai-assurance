# Connected audit workflow — implemented 7 October 2026

The hosted workspace now implements the seven business workflows described in `workflow-product-plan.md`. The primary work surface is **Audit program**. Planning, Fieldwork, Evidence evaluation, Reporting and Sign-off remain the engagement lifecycle. The new work spine does not add seven competing navigation modules.

## What auditors can complete

| Workflow | Implemented records and decisions | Main surface |
| --- | --- | --- |
| Engagement acceptance and scope | Versioned brief: system/use, audit period, boundary, actor responsibilities, audience, deliverables, criteria/dates, constraints and independence. Submit, independently approve or return; a return records the reviewer's reason apart from the preparer's change impact. Approved scope changes invalidate program approval and require impact review. | Audit program → Engagement brief |
| Scope-specific program | 33 methodology candidates with verbatim objectives, steps and expected evidence. Selection is separate from applicability. Bulk human scope decisions; individual criteria, source version, period analysis, sampling, preparer/reviewer, deadline and manual/automated method. Independent program approval; preparer, reviewer and deadline changes need none. | Audit program → Program |
| Actual procedure work | Plan → Execute → Evaluate → Review. Explicit performed/omitted steps, actual sample, results, evidence and limitations; relevance, reliability, coverage, contradictions and reasoned human conclusion. Pinned evaluations and direct evidence/finding handoffs. | Procedure workspace |
| Independent review | Scope/program review and assigned procedure review; return/rework; attributed responses to questions; question-author resolution; compilation to revision-controlled papers and separate Lead sign-off. Compiled narratives change through their source procedure. | Review inbox / paper comments |
| Controlled report issuance | Immutable internal and client snapshots. Readable captured scope/program trail, exact client preview, independent two-digest approval, separate Lead release, withdrawal and supersession history. | Reports → Package details |
| Client collaboration | Distinct Client Contributor role, client assignment, expiring per-request grants, safe instructions, own submissions/downloads, partial/complete delivery and outstanding items. Internal receipt acceptance and evidential sufficiency remain separate. Independently authored client clarification never exposes internal assessment. | Evidence vault → Requests; contributor portal |
| Post-issue follow-up | Finding support, attributed management remediation, independent retest with performed work/results/rationale, closure/reopening history; monitoring/change/incident/remediation cases, impact decisions, atomic linked successor engagement and independent case closure. Linked next monitoring cycles have explicit due dates. | Findings; Audit program → Follow-up |

New engagements start with draft program candidates and no precreated completed-looking papers. Existing engagements adopt explicitly; signed content and reports are preserved. An independently approved exclusion affects whether its linked legacy paper is required for this engagement, without rewriting that paper. Limitation memos remain required and must be evaluated, reviewed and signed. An applicable procedure omitted from audit scope prevents a positive readiness opinion; qualified/adverse/unable-to-conclude reports remain subject to documented completion gates.

Earlier final snapshots without a release history remain available internally. They are not automatically represented as independently approved or client-released. A new issuance must capture the current approved program and completed review packet; release cannot retrofit those facts into a legacy snapshot.

## Common execution and technical controls

`lib/workflow-types.ts` is the application contract. `schemas/procedure-execution.schema.json` describes the portable actual-execution record; `schemas/test-run.schema.json` extends hosted run 1.1 with exact procedure/scope bindings and retry lineage.

A procedure plan has a substantive part (selection, applicability, rationale, criterion, source version, period analysis, population, sampling, method and pinned inputs, with the methodology objective and steps) and an assignment (preparer, reviewer and due date). The plan revision and a SHA-256 plan hash cover the substantive part only; the assignment has its own revision. An execution binds the plan hash and the brief revision, so it stays current until its own procedure's substantive plan or the scope changes: changes to other procedures, and the program revisions they create, never invalidate it. A substantive change returns an approved program to draft and invalidates that procedure's execution and review only; reviewed work goes back for review, so restoring its plan makes the execution current again but not the review. An assignment change keeps the program approval and recorded work; reviewed work keeps its reviewer, and approved work keeps a preparer, reviewer and deadline. Executions recorded before plan hashes keep their plan-revision binding. Because the plan form carries the assignment, a plan save names the assignment revision it was opened at and is refused with 409 if the preparer, reviewer or due date changed since, instead of reverting that change. A saved recovery draft of the plan form is dated by the assignment revision as well as the plan, execution, program and scope revisions, so after a reassignment it is offered only for export and comparison, not restored; execution and evaluation drafts, which hold no assignment, stay restorable.

Histories keep submissions, not drafting. A brief, program or procedure plan is amended until its next submission. The program history records each submission and its outcome: approval, return with the reviewer's reason, or withdrawal when a Lead's plan or scope change takes it back to draft. The brief history keeps each returned revision and each approved revision a Lead revises. A procedure keeps its plan as submitted at its first change after a submission, a review that a plan change clears, and its state before each execution, evaluation, impact review and return, each entry marked with the change that followed it. A brief return stores `returnReason`, `returnedBy` and `returnedAt` instead of rewriting the preparer's change impact.

History limits never stop a change halfway. The scope and the program count returns only, 40 and 75: a submission that is approved or withdrawn uses none, so an approved scope or program always has a submission left, and a plan change or scope change made to it can always be submitted and approved again. Returns are never refused; a scope or program returned to its limit can still be drafted but not submitted again. A change that would need a submission the limit refuses, possible only if a limit is lowered, is refused before it lands, and the approved records stay in force. A procedure counts 30 work revisions (executions, evaluations and impact reviews; plan changes and returns use none), and at its limit only redoing current work is refused: the first execution and evaluation, new work or an impact review after a plan or scope change made the work stale, plan changes and reassignments are always accepted. The audit program warns five returns or work revisions before a limit.

An entry's shape, never its date, decides whether it counts. Every procedure history entry the commands write records its `action`; an entry without one was written before actions existed and counts towards no limit, whenever it was written, so a procedure that reached the earlier 30-entry limit can be reassigned, replanned and worked on again. Likewise, returned brief revisions without a `returnReason` and older program entries, none of which is a "returned" entry, are not counted.

Approval cycles and Lead withdrawals count towards no history limit; the engagement's 1.5 MB metadata limit bounds them. For a program of 33 procedures, each submission and each approval or withdrawal adds an entry of about 4 KB that binds every procedure's plan revision and hash, so a cycle adds about 8 KB: roughly 170 cycles fit in an otherwise small engagement, fewer as its other records grow. `save()` in `lib/engagement-repo.ts` measures the stored (dehydrated) engagement before the single D1 batch that writes the engagement, its snapshot and its audit event, and refuses with 413 before anything is written:

- A write that would take the record over 1.5 MB: "This change would take the engagement record over its 1.5 MB limit. Nothing was saved. Shorten the text you are adding, or continue in a follow-up engagement."
- So that the limit never stops an approval halfway, 100 KB under it are kept for approving the scope and program (`metadataReserve()` in `lib/workflow-state.ts`). A write that starts an approval (adopting the workflow, or taking an approved scope, an approved program or a submitted program back to draft) must leave all 100 KB free, or it is refused with "This change would need the engagement scope or audit program to be approved, but would leave less than the 100 KB that approval needs …". The approved scope, program and plans then stay in force exactly as they were, and changes that need no approval (such as a preparer, reviewer or due date) still go through.
- A submission of the scope or program must leave room for the reviewer to approve or return it (the submitted record plus two 2,000-character reasons).
- Once a cycle has started, its own writes may use the reserve: drafting the brief and plans, and the reviewer's approvals and returns. While the scope or program awaits approval, any other write may not grow the record into the reserve (or into the room kept for a pending decision, if larger). A Lead's change that would withdraw a submission inside the reserve is refused, since it would start another cycle; the reviewer can still return or approve it.

From 200 KB before the limit, the audit program warns how much of it is used and what the reserve refuses (`metadataWarning()`; the workspace view passes the stored size to internal roles). Content-addressed R2 objects that a refused write had already stored stay unreferenced, as after a lost version check. Further approval cycles then belong in a follow-up engagement.

An approved automated/mixed procedure pins the registered model version, accepted prediction dataset and immutable evaluation protocol. Queueing rejects mismatched pins. Each run carries a SHA-256 of its procedure/brief/program binding alongside existing manifest, configuration, model and dataset hashes. Execution verifies frozen bindings and input bytes. Compilation accepts only succeeded runs bound to the procedure's current plan revision and the current brief revision, with the planned inputs; a run queued under an earlier program revision still counts. A technical outcome never substitutes for the auditor's evidence evaluation.

Failed/cancelled evaluations can be queued as a new retry after input integrity and current scope are revalidated. The prior result is preserved and `retryOf` records lineage. Interactive jobs use a guarded queued → running claim and guarded completion; concurrent edits do not silently overwrite state. Recovery is explicit for interrupted claims. Hosted execution remains bounded saved-prediction diagnostics, not a separately provisioned native-model worker fleet.

`/api/report-package` verifies the captured report's SHA-256 and returns a deterministic reference manifest of captured paper hashes and evidence pins. Authorized users can download the corresponding verifiable package. Client users receive only a currently released client projection. Withdrawal/supersession removes access to that projection while preserving internal snapshot bytes and both digests. Verification does not assert external timestamping, qualified signatures, or that every R2 object was reread.

Every mutation uses engagement/management version checks and same-origin enforcement. Winning D1 commands append a snapshot and audit event atomically. The membership guard rechecks active role **and client assignment**, preventing a same-role reassignment from authorizing an old client upload. Grant revocation changes the engagement version; losing file writes are cleaned up. Client projections use explicit allowlists and do not include internal brief/program/procedure records, user directories, audit events or internal request descriptions.

Release rejects source records changed after capture, including procedure executions, reviewed papers, requests, findings, classification, the evidence manifest, model metadata, evaluation profiles and diagnostic runs. Prior approvals are tied to exact captured digests. Scope/program approval is independent of cumulative preparers; requesting corrections does not make the reviewer a preparer. Procedure review is restricted to its assigned independent reviewer; paper sign-off remains separate.

## Validation and operating boundaries

The integration fixture runs against ephemeral Miniflare D1/R2 storage, with fictional identities and synthetic evidence. It exercises the full journey, negative permissions, concurrent management commands, role revocation, exact input pins, compiled-paper boundaries, partial receipts, report release/withdrawal/projection, package verification, finding retest and linked successor creation. No production audit records or access grants are created for QA.

The current hosted aggregate has a 1.5 MB per-engagement limit and bounded histories. The normalized production architecture and separate Python execution service remain documented separately. Native binary adapters, isolated asynchronous external workers, SQL credentials, automated monitoring schedules and external notifications are not newly deployed by this increment. Monitoring recurrence is an explicit planning action. Current legal applicability, evidence sufficiency and assurance opinion require competent human decisions using the recorded regulatory source and audit-period analysis.

## Business workspace usability

The personal work inbox derives actions from procedures and their dependencies across authorized engagements, with server-stored views and reminder preferences. Procedure workspaces connect accepted evidence, client requests, sampling records, current diagnostic runs, findings, and saved review comparisons. Private recoverable drafts remain separate from audit revisions and require explicit saving; stale drafts cannot overwrite a changed audit basis.

Member onboarding combines role selection, engagement assignments, and a review step. Client request packages support required-item checklists, multiple files, clarification threads, and separate receipt acknowledgment and evidence acceptance. Site access remains a separate host permission. Reminders are in-app; no email delivery is configured.

Dataset cards are immutable versions tied to accepted artifact hashes and optional baseline pins. Testing readiness evaluates the exact procedure, protocol, input, execution mode, and native execution approvals before queue handoff. Bulk planning checks assignments and reviewer independence before revising a program. Permission-checked links and contextual text previews preserve engagement access boundaries.

Shared form grids align labels and controls consistently, including native date fields, wrapped labels, and optional field guidance. Mobile forms stack and use 44px controls.
