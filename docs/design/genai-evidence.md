## 1. Key conclusions

1. **Ingest, recompute, attest.** The platform reads the per-item records that Inspect, lm-evaluation-harness, promptfoo, garak, PyRIT, DeepEval and Ragas already write, recomputes every statistic itself, and binds the result to the hashed source logs. It runs no red-team harness, never executes or imports anything an ingested file names, and embeds no tool code (all seven tools are MIT or Apache-2.0; none is embedded anyway).
2. **Four evidence levels, computed, never typed in.** L0 is a reported aggregate, L1 a hashed and identified tool log, L2 statistics recomputed by our engine from per-item records, L3 an L2 recomputation of a run the auditor executed, backed by an attestation record. An envelope uploaded by hand rather than returned by an enrolled worker counts as at most L1 for the readiness gate (section 4).
3. **Every format was read from real output.** Section 7 maps each format field by field, from fixtures generated by running each tool offline on 5 November 2026. Several facts only showed up in real files and change the parsers:
   - Inspect `.eval` files are zip archives whose entries are **zstd-compressed** (method 93). Python's standard library reads them only from 3.14, and CI runs 3.11. Reading them needs the optional `zstandard` package (BSD-3-Clause) until then.
   - Inspect writes unscored values as bare **`NaN`** tokens, which are not valid JSON. This comes from its source (`Score.model_config`); the fixtures contain no unscored samples.
   - Inspect keeps post-run edits in `log_updates`, `Score.history` and sample `invalidation`.
   - garak writes **naive local timestamps** and tags probes with the **2023** OWASP LLM numbering. promptfoo uses the **2025** numbering.
   - PyRIT 1.1.0 has **no file exporter**.
   - DeepEval and Ragas files carry **no harness version or model identity**.
4. **One per-item record and one run-metadata block for every tool.** The record keeps hashes, scores, edit provenance, judge references, epoch, technique, categories and a cluster id, but not raw text. The run metadata records, for each required field, whether it was extracted, declared, computed or is missing (section 6). The draft schema validates all 122 records produced from the fixtures.
5. **The interval decides, as in `docs/design/audit-statistics.md`.** GenAI criteria reuse that design's bands, members, interval inversion, intersection-union pass, within-criterion Bonferroni fail and Holm/BH families (section 8). This design adds:
   - the clustered standard error of Miller (2024), in the finite-cluster-corrected form Inspect implements;
   - a Wilson interval on the design-effect-adjusted sample size, so that clustering or epoch averaging never produces a zero-width interval;
   - attack-success rate per technique with Wilson intervals, on attack items after reducing repeats (default: an attack succeeds if any repeat succeeds);
   - pass^k and pass@k for agents;
   - paired differences between models;
   - Cohen's kappa, with the Fleiss–Cohen–Everitt standard error, for judge validation.
6. **A judge counts as validated only if** it comes from a different model family than the system under test (developer-level family, declared and cross-checked) and its kappa against human labels has a 95% lower bound of at least 0.60 on at least 50 items. Pairwise judges also need position-swap consistency with a Wilson lower bound of at least 0.80. Judges favour their own and similar outputs, so a same-family judge is not independent evidence (section 8.7).
7. **Post-run edits are evidence, not noise.** By default the engine recomputes from the scores the run produced. It lists every edit (author, time and a hash of the reason), also computes the as-edited view, and reconciles with the tool's own aggregates. The gate requires a reviewer acknowledgement before an edited log supports a conclusion.
8. **Where it runs.** Parsing and recomputation happen in the engine: through `python -m engine.genai` locally, or as a new `genai_ingest` job of the existing external pull worker. The worker returns the exact result bytes under the existing HMAC completion signature. A Cloudflare Worker cannot do this job:
   - it is limited to 128 MB of memory;
   - the Compression Streams API has no zstd;
   - it has no sandbox for re-runs.

   Hashed parts of the envelope travel as exact JSON strings, so Python and TypeScript never need to agree on float formatting (section 10).
9. **Security posture.** Parsers are pure functions over bytes:
   - bounded sizes, depth, counts and decompression ratio, with an enumerated error code for every rejection;
   - no `pickle`, YAML, `eval`, imports, regexes taken from the input, network or subprocesses;
   - secret-like values are never copied out of tool configuration.

   A deterministic mutation fuzzer and property tests run in CI for every format (section 11).
10. **Mappings are data, translated by name.** 26 GenAI risk categories map to the OWASP Top 10 for LLM Applications (2026), the OWASP Top 10 for Agentic Applications (December 2025), NIST AI 600-1, MITRE ATLAS v2026.10 and AI Act Art. 15(5), Art. 50 and Art. 55(1)(a) (section 9). Tool tags are translated by entry name, never by number, because the tools use different OWASP editions. The 2026 OWASP identifiers come from secondary sources and must be confirmed against the official document before #33 releases the pack.
11. **Plan: #32 in six pull requests, then #33 in three** (section 13). #32 delivers Inspect, lm-evaluation-harness, promptfoo and garak first, then DeepEval, Ragas and PyRIT.

## 2. Scope, principles and non-goals

**In scope.** Reading evaluation outputs of the seven tools above; a normalized per-item record; required run metadata; evidence levels; recomputed statistics with decisions; judge validation; mappings to risk frameworks; the engine CLI and worker job; the workspace intake, results view and readiness gate (#33); security and fuzzing.

**Principles.**

- **Ingest, recompute, attest** (direction of 5 November 2026). The harness belongs to the client or the auditor; the platform is the independent verification layer.
- **Never execute ingested code.** No re-scoring, no `trust_log`, no task files, no `!function` hooks, no JavaScript assertions, no templates rendered. A log that names code is ingested as data.
- **Method before runner** (research synthesis, section 5.1). The test plan, including bands, the primary score and the judge rules, is frozen before ingestion (AI Act Art. 9(8) asks for testing "against prior defined metrics and probabilistic thresholds").
- **Claims are scoped.** Benchmark accuracy is not accuracy on the population of real inputs (NIST AI 800-3), and a low attack-success rate holds only for that attack set, configuration and judge. Every result carries generated claim-scope statements (section 8.10).
- **No AGPL code is embedded.** The parsers are independent implementations of published or observed formats.

**Non-goals.** Running red-team or benchmark harnesses on platform infrastructure; hosting benchmarks; a default LLM-judge service; continuous monitoring; C2PA or watermark validation (R6.5, separate issue); L3 re-runs executed by the worker itself (R6.4, P2). Section 10.6 fixes the attestation shape those re-runs will use.

## 3. Current state (checked on `main@b15f037`)

- **Nothing evaluates or ingests GenAI evidence.** No file in `engine/`, `site-app/` or `schemas/` parses any of the seven formats.
- **External worker.** `engine/worker.py` and `engine/worker_contract.py` implement a pull protocol against `site-app/app/api/runner/route.ts`:
  - leased and fenced attempts;
  - exact `requestJSON` bytes with `requestSha256`;
  - downloads by `input=dataset|model`;
  - a completion carrying the exact `resultJSON` string, signed with `X-Result-Signature`, an HMAC-SHA256 keyed by SHA-256 of the worker token.

  Results are limited to 8 MiB (`MAX_RESULT_BYTES`), completion bodies to 10 MiB and the route's `resultJSON` to 9 MiB. The route accepts only the tabular envelope (`resultEnvelope` in `site-app/lib/assurance-core.ts`: `externalReport` plus `hostedResults`). Claims match on `executionMode` and model format. Enrollment accepts the formats `provided_predictions`, `ONNX`, `XGBoost`, `LightGBM` and `PMML`.
- **Evidence intake.** `site-app/app/api/evidence/route.ts` accepts files up to 50 MB, stores them in R2 under content-addressed keys with their SHA-256, and gives them a disposition. `site-app/lib/assurance-store.ts` `recordStatement` creates immutable hashed assurance records attributed to the actor. Records are not cryptographically signed and are limited to 150,000 bytes.
- **Engine conventions to reuse.** `strict_json` in `engine/worker_contract.py` and `_loads` in `engine/assurance.py` give bounded UTF-8 JSON with duplicate-key and non-finite rejection. The engine also provides `canonical_bytes` (sorted keys, compact, `ensure_ascii=False`) and create-once outputs. `wilson()` in `engine/diagnostics.py` uses z = 1.959963984540054. Coded errors (`engine/errors.py`, PR #47) carry an enumerated `code`.
- **Runtime.** The core engine is standard-library only. CI runs Python 3.11 (`.github/workflows/ci.yml`), while `engine/Dockerfile` uses 3.12.14. `engine/requirements-dev.txt` is the place for test-only packages.

## 4. Evidence levels

### 4.1 Definitions

| Level | Meaning | Typical source |
|---|---|---|
| **L0** | **Reported aggregate.** A number someone states (vendor report, model card, a tool's summary line), or a tool file that holds aggregates only | A PDF benchmark table; lm-evaluation-harness results without `--log_samples`; a promptfoo `stats` block without `results` |
| **L1** | **Hashed tool log.** The exact bytes of a recognised tool output are pinned by SHA-256 and identified (format, version, run identity), but our statistics could not be recomputed from per-item records | Unverified tool version; `--predict_only` samples without scores; parse succeeded only for metadata; a manually uploaded envelope (custody cap) |
| **L2** | **Recomputed by us.** The engine extracted per-item records and recomputed every reported statistic from them, under a frozen plan, with reconciliation against the tool's aggregates | Any supported format parsed in full |
| **L3** | **Re-run by the auditor, with attestation.** An L2 result whose source logs come from a run the audit team executed itself, bound by an attestation record that pins those logs | Auditor-run Inspect, garak or promptfoo, then ingested through the worker |

### 4.2 Assignment (normative)

The engine assigns `L0`, `L1` or `L2` to each run in a bundle. The workspace derives the **effective level** used by the gate.

1. A run is **L2** when all of the following hold:
   - every input file was hashed, matched its declared SHA-256 and was identified as the declared format;
   - the format-version gate passed (section 7.10);
   - at least one item has status `scored`;
   - every item that feeds a criterion was parsed;
   - no `tool_hash_mismatch` occurred (section 7.1).
2. Otherwise the run is **L1** if the file was hashed and identified.
3. Otherwise it is **L0**. Aggregates entered by hand in the workspace are also L0; they are a record kind of #33, not an engine output.
4. A comparison (paired difference) takes the lower level of its two runs. Judge validation has its own level: L2 when recomputed from a pinned label file, L0 when only a kappa value is declared.
5. **Workspace effective level.**
   - `effective = engine level` when the envelope arrived through an authenticated `genai_ingest` worker completion.
   - `effective = min(engine level, L1)` when the envelope was uploaded by a person. The upload is still stored and shown, labelled "auditor-prepared, unauthenticated computation". It becomes authenticated only when a worker recomputation of the same inputs, plan and engine version yields the same `computationSha256`.
   - `effective = L3` when the engine level is L2, the bundle's `origin` is `auditor_rerun`, and a `genai_rerun_attestation` record exists. That record must be created by an Auditor or Lead Auditor (never a client role) and must pin every input SHA-256 of the bundle (section 10.6).

Post-run edits, missing metadata and reconciliation mismatches do **not** lower the level. Level describes how the evidence was obtained. The other three are separate gate conditions (section 12.3), so the UI shows them separately and never folds them into one badge.

## 5. Data model

```text
evidence artifacts (R2, SHA-256)          frozen plan (genai-plan/0.1)        bundle manifest (genai-bundle/0.1)
  raw tool logs, judge label files          criteria, bands, primary score      declared metadata, input pins,
            |                               policies, judge rules               judge bindings, origin
            +-------------------------+-------------------------------------------+
                                      v
                       engine.genai: detect -> parse -> normalize -> recompute
                                      |
            +-------------------------+---------------------------------+
            v                                                           v
   items.jsonl (genai-evidence-item/0.1)                 result envelope (genai-result/0.1)
   one record per item and epoch                           computationJSON + computationSha256,
                                                           items inline when <= 4 MiB, provenance
```

- **Bundle**: one or more input files from one tool run, plus the manifest. A bundle can contain several runs: promptfoo writes one run per provider, and lm-evaluation-harness writes one results file plus one samples file per task.
- **Run**: one system under test evaluated on one task set by one harness invocation. It has a `runKey` (section 7) and its own run metadata.
- **Item**: one test item at one epoch. Repeats of the same test item share a `groupKey` and are reduced before statistics are computed (section 8.2).
- **Plan** (frozen before ingestion) and **manifest** (declarations by an auditor) are both strict JSON. Unknown keys are rejected. They are specified in sections 8.1 and 6.3, and their JSON Schemas are written in #32 (`schemas/genai-result.schema.json` `$defs`).

## 6. Required run metadata

### 6.1 Fields and rules

Every run carries `$defs/runMetadata` from `schemas/genai-evidence-item.schema.json`. Each field has a `source` of `{kind: extracted | declared | computed | missing, pointer, declaredBy}`.

| Field | Content and rule |
|---|---|
| `harness` | Tool name and version. Extracted where recorded (Inspect `eval.packages.inspect_ai`, `lm_eval_version`, `metadata.promptfooVersion`, garak `_config.version`, `pyritVersion`); otherwise it MUST be declared (DeepEval, Ragas) |
| `systemUnderTest` | `model` (as recorded), `snapshot`, `provider`, `family`. `snapshot` MUST identify an immutable version: a dated snapshot, a revision hash or a digest. Aliases that can move (`latest`, `default`, an undated name such as `gpt-4o`) give `snapshot: null` and the warning `moving_model_alias`. Inspect records in each sample's `output.model` the model name the provider returned. For APIs that return the resolved snapshot this is the snapshot; it was verified here only with `mockllm`. When it differs from `eval.model`, the distinct values are the extracted snapshot; more than one distinct value adds `snapshot_changed_during_run`. `family` is declared (section 8.7) |
| `systemPrompt` | SHA-256 of the exact system prompt text sent (section 6.2), and `distinctCount`. If items carry more than one distinct system prompt, the run-level hash is null with `multiple_system_prompts`, and each item keeps its own |
| `decoding` | `temperature`, `topP`, `topK`, `maxTokens`, `seed`, `generationsPerItem`, plus up to 30 other scalar settings. Only allowlisted keys are copied (section 11.4) |
| `tools` | `agentic` (true, false or null) and the tools offered, as `{name, permission, definitionSha256}`. Permission is one of `read`, `write`, `execute`, `network` or `unknown`. Logs carry tool definitions but never their permissions, so permissions MUST be declared for agentic runs |
| `dataset` | Name, version and SHA-256 when known. The engine always adds a computed **dataset fingerprint**: SHA-256 of the canonical JSON of the sorted `[groupKey, promptSha256, targetSha256]` triples. Two runs with the same fingerprint evaluated the same items, which pairing requires |
| `attackSet` | For attack criteria: name, version and hash (for example garak probe spec plus garak version; promptfoo `config.tests`, hashed as canonical JSON) |
| `judges` | One entry per judge model: `ref` (`J1`, `J2`, …), `role` (`grader`, `pairwise_judge`, `detector_model`, `scorer_model`), `model` (with snapshot and family), `promptTemplateSha256`, and `validation` (kappa, interval, n, level, label-file SHA-256, evidence level) |
| `epochs` | Repeats per test item (Inspect `config.epochs`, promptfoo `repeat`, garak `run.generations`), otherwise 1 |
| `n` | Computed: `items`, `groups` and `scored` |
| `dates` | `runStartedAt` and `runCompletedAt`, timezone-aware. Naive timestamps (garak) are converted only when the manifest declares `dates.utcOffset` (for example `"+01:00"`); otherwise they are null with `naive_timestamp` |
| `completeness` | `missing` and `declaredOnly`: lists of the field names in `$defs/metadataFieldList` |

A required field is **missing** when it is null after extraction and declaration. Which fields are required depends on the criteria:

- Every GenAI conclusion needs `harness`, `systemUnderTest.snapshot`, `systemUnderTest.family`, `systemPrompt`, `decoding`, `tools`, `dataset`, `epochs` and `dates`.
- Attack criteria also need `attackSet`.
- Criteria fed by a model-graded score also need `judges.model`, `judges.family` and `judges.validation`.

`systemPrompt` counts as present when a hash was extracted or declared. A declaration that the system had no system prompt is recorded as the SHA-256 of the empty string.

### 6.2 Hashing and normalization rules (normative)

- SHA-256 over UTF-8 bytes, lowercase hex. Texts are hashed **exactly as recorded**: no Unicode normalization, no trimming, no line-ending changes. This keeps tool-provided hashes cross-checkable.
- **Message normalization** for structured inputs:
  - each message becomes `{"role": role, "content": content}`;
  - string content stays as is;
  - list content (multi-part) stays as the recorded JSON list;
  - Inspect `attachment://<32 hex>` references are first replaced by `sample.attachments[<id>]`. A missing attachment leaves the reference string in place and adds `unresolved_attachment`.
- **`promptSha256`**:
  - if the tool records the model input as one string (lm-evaluation-harness `arguments.gen_args_0.arg_0`, a non-chat promptfoo `prompt.raw`), it is SHA-256 of that string;
  - otherwise take the normalized input messages **without** system messages. If exactly one message remains, its role is `user` and its content is a string, hash that string; otherwise hash the canonical JSON of the list.
- **`systemPromptSha256`**: one system message gives SHA-256 of its text (multi-part content as canonical JSON); several give SHA-256 of the canonical JSON array of their texts.
- **`responseSha256`**: SHA-256 of the final response text of the system under test. Structured outputs are hashed as canonical JSON. The value is null when the item errored or has no generated text (log-likelihood tasks).
- **`transcriptSha256`** (agent items): canonical JSON of the full normalized message list, including tool calls and tool results as recorded.
- **Canonical JSON** is `engine.diagnostics.canonical_bytes`, byte-identical across engine versions. Canonical JSON is never recomputed in TypeScript (section 10.3).
- **Keys** match `^[A-Za-z0-9._:|/#@+=-]{1,512}$`. `itemKey` = `<runKey>|<groupKey>|<epoch>` MUST be unique within an envelope. Duplicates are the error `duplicate_item_key`. Occurrence counters (`:<n>`) number repeated identical prompts in file order, starting at 0.

### 6.3 Bundle manifest (`genai-bundle/0.1`)

```json
{
  "schemaVersion": "genai-bundle/0.1",
  "origin": "auditee_supplied",
  "inputs": [
    {"name": "judged_qa_30.eval", "sha256": "e29d615a…", "bytes": 92626, "format": "inspect_eval", "role": "log"},
    {"name": "judge_large_200.jsonl", "sha256": "29092dd6…", "bytes": 25800, "format": "judge_validation_jsonl", "role": "judge_validation", "judgeRef": "J1"}
  ],
  "declared": {
    "systemUnderTest": {"snapshot": "fixture-sut-2026-11-05", "provider": "fixture", "family": "other-fixture-sut"},
    "tools": {"agentic": false, "offered": []},
    "dataset": {"name": "judged_qa_30", "version": "1.0.0"},
    "judges": [{"ref": "J1", "model": "mockllm/judge", "snapshot": "fixture-judge-2026-11-05", "family": "other-fixture-judge", "promptTemplateSha256": null}],
    "dates": {"utcOffset": null}
  },
  "declaredBy": "USER-…",
  "declaredAt": "2026-11-05T17:00:00Z"
}
```

- `origin` is `auditee_supplied` or `auditor_rerun`.
- Inputs are matched to files by SHA-256, never by name or path.
- `role` is one of `log`, `samples`, `results`, `hitlog`, `judge_validation` or `attack_set`.
- A declaration never overrides an extracted value. Both values are kept and the warning `declaration_conflict` is added when they differ after the following comparison: strings compared exactly; `snapshot` may refine `model` when it starts with the last `/`-separated segment of the extracted model name.
- The judges' `ref` values are matched to judges found in the log by model name. A declared judge that is never observed raises `declared_judge_not_observed`. An observed judge that is never declared stays with `family: null`.

## 7. Formats (field-level mapping)

All mappings below were checked against the fixtures in `engine/tests/fixtures/genai/` (versions as listed there). `normalized-examples.json` shows the first normalized record and the run metadata of each fixture.

### 7.1 Rules common to all formats

- **Detection** uses content, never the file name. The detected format MUST equal the manifest's `format` (`format_mismatch`). Detection signatures are given per format below.
- **JSON reading** is strict UTF-8, through `engine.genai.readers`: an optional BOM is rejected (`invalid_utf8`), duplicate keys are rejected and size, depth and counts are bounded (section 11.3). **Non-finite tokens** (`NaN`, `Infinity`, `-Infinity`) are accepted because Inspect and lm-evaluation-harness write them. They are decoded to an internal `NonFinite` marker, never to a float. Wherever a number is expected, the marker becomes `null` with `non_finite_score`; anywhere else the field is treated as absent.
- **JSONL**: lines split on `\n` (a trailing `\r` is stripped and counted in `crlf_lines`); blank lines are skipped and counted; every other line MUST be one JSON object. The locator is `<file name>:<1-based line>`.
- **Tool-reported hashes** (lm-evaluation-harness `doc_hash`, `prompt_hash`, `target_hash`; PyRIT `original_value_sha256`, `converted_value_sha256`) are recomputed. Any mismatch adds `tool_hash_mismatch` with the locator and caps the run at L1. Inconsistent hashes inside a tool's own file are a tampering or version signal.
- **Status**:
  - `error`: the tool recorded an error for the item;
  - `unscored`: no mappable primary score;
  - `invalidated`: Inspect sample invalidation, only under the `as_edited` policy;
  - `scored` otherwise.

  Only scored items enter denominators. The counts of the other three statuses are always reported.
- **Labels** keep at most 50 scalar metadata entries (keys `^[A-Za-z0-9_.:-]{1,100}$`, string values truncated to 500 characters with `label_truncated`). Objects, arrays and keys starting with `_` are dropped.

### 7.2 Inspect AI (`inspect_eval`, `inspect_json`)

**Detection.** `inspect_eval` is a zip (`PK\x03\x04`) whose central directory contains `header.json`, or `_journal/start.json` for an unfinished log. `inspect_json` is a JSON object with `version` and the keys `eval` and `plan`.

**Version gate.** Log `version` MUST be 2. `eval.packages.inspect_ai` verified: 0.3.287.

**Zip handling (`.eval`).** Observed entries:

- `header.json`
- `samples/<id>_epoch_<n>.json`
- `reductions.json`
- `summaries.json`
- `_journal/start.json`
- `_journal/summaries/<n>.json`

All of them use compression method 93 (zstd) in 0.3.287: Inspect switched to zstd in 0.3.206 ([eval logs](https://inspect.aisi.org.uk/eval-logs.html)) and monkey-patches `zipfile` with `zipfile_zstd` below Python 3.14.

The engine reads the central directory with stdlib `zipfile` and only then decompresses each entry it needs, choosing a back-end by method:

| Method | Back-end |
|---|---|
| 0 (stored), 8 (deflate) | stdlib |
| 93 (zstd) | stdlib `compression.zstd` on Python ≥ 3.14; otherwise the optional `zstandard==0.25.0` |
| any other | rejected: `zip_method_unsupported` |

When neither zstd back-end is present, the result is `zstd_unavailable`. Decompression MUST stream with an output cap, verify the CRC-32 and enforce the zip limits of section 11.3.

Entry names are data. Only the names above are read; others are listed in `ignored_entries` and never interpreted. The sample entries are authoritative. `summaries.json` and the journal are used only to cross-check sample counts (`summary_count_mismatch`).

| Per-item field | Source |
|---|---|
| `runKey` | `inspect:<eval.eval_id>` |
| `groupKey` | `<eval.task_registry_name or eval.task>:<sample.id>`, with `sample.id` converted to a string |
| `epoch` | `sample.epoch` |
| `source.toolItemId` | `sample.uuid` |
| `task` | `eval.task`, `eval.task_version` |
| `promptSha256` | `sample.input`: a string becomes one user message, a list is taken as recorded; hashed with the rule of section 6.2 |
| `systemPromptSha256` | `sample.messages[role="system"]` |
| `responseSha256` | `sample.output.completion` |
| `transcriptSha256` | `sample.messages`, for agent items |
| `targetSha256` | `sample.target`: a string as is; a list as canonical JSON |
| `scores[]` | One per `sample.scores[name]`. `raw` is `history[0].value` under the `original` policy and `value` under `as_edited`. `value` maps `C` = 1, `P` = 0.5, `I` = 0 and `N` = 0; numbers stay numbers, booleans become 1 or 0, and the strings `yes`/`true` and `no`/`false` become 1 and 0. Anything else is `null` with `unparseable_score`: Inspect itself maps such values to 0 with a warning, and the engine deliberately does not. `edited` is true when `history` has more than one entry. `edits[]` holds `{at, author, reasonSha256}` from each later history entry's `provenance` |
| `scores[].scorer.kind` | `model_graded` when the scorer's span contains a `model` event with `origin: "scorer"`. Its `judgeRef` is the judge whose model equals that event's `model`. Otherwise `deterministic` |

| `clusterId`, `technique` | `sample.metadata[plan.clusterKey]`, `sample.metadata[plan.techniqueKey]` (the technique defaults to the task name) |
| `labels` | Scalar `sample.metadata` entries |
| `usage`, `timing` | `sample.model_usage[eval.model]`; `sample.started_at` and `sample.completed_at` |

| Run metadata | Source |
|---|---|
| `harness` | `inspect_ai` with `eval.packages.inspect_ai` |

### 7.6 PyRIT (`pyrit_export`)

PyRIT 1.1.0 keeps results in its memory database (SQLite or Azure SQL). ### 8.1 Plan (`genai-plan/0.1`)

### 8.2 Item outcomes and epoch reduction

1. Each scored item gets `y = outcome.value ∈ [0, 1]` from the primary score, using `successRule`. `correct` and `attack_success` are 0 or 1; `score` may be fractional.
2. Items are grouped by (`runKey`, `groupKey`). The group outcome is the plan's reducer over its scored epochs:
   - `mean` is the arithmetic mean;
   - `any` is 1 when any epoch is 1;
   - `all` is 1 when every epoch is 1;
   - `majority` is 1 when more than half are 1; for `attack_success`, when at least half are 1.
   A group with no scored epoch is `unscored`.
3. Statistics use **groups**, never raw epochs. Repeated answers to one question are not independent, and Miller (2024, section 3.1) computes the standard error across question-level means. `n` is the number of scored groups.
4. Variation across epochs is reported, never used for decisions: the number of groups whose epochs disagree (`unstableGroups`, as promptfoo reports) and the mean within-group variance. Outputs vary across runs even at temperature 0 because of batch-dependent inference ([Thinking Machines](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/)).

### 8.3 Mean scores (accuracy, score means): standard errors and intervals

For group outcomes y₁…yₙ with mean ȳ:

- **IID standard error** (Miller 2024, eq. 1; also Inspect's `stderr` and lm-evaluation-harness's `*_stderr`):
  `SE_iid = sqrt( Σ (yᵢ − ȳ)² / (n(n − 1)) )`.
- **Clustered standard error**, when `clusterKey` is set (Miller 2024, eq. 4, with the finite-cluster correction C/(C − 1), exactly as `_clustered_stderr` in Inspect's `scorer/_metrics/std.py` implements it):
  `SE_cl = (1/n) · sqrt( C/(C − 1) · Σ_c ( Σ_{i ∈ c} (yᵢ − ȳ) )² )`, where C is the number of distinct cluster ids.
  With one item per cluster it equals `SE_iid` exactly (property test). It requires C ≥ `minimums.clusters`, otherwise the member is `insufficient_support` with `below_minimum_clusters`. Inspect returns 0 for C < 2; the engine does not.
- **Decision interval: Wilson on the effective sample size.**
  1. If every yᵢ ∈ {0, 1} and there is no `clusterKey`, use the Wilson score interval on x = Σyᵢ out of n ([Wilson 1927](https://doi.org/10.1080/01621459.1927.10502953)). This is `docs/design/audit-statistics.md` section 5.1 exactly.
  2. Otherwise compute `SE` (clustered if `clusterKey`, else IID) and the effective sample size `n_eff = min(n, ȳ(1 − ȳ)/SE²)`, with `n_eff = n` when SE = 0 or ȳ ∈ {0, 1}. Then compute Wilson on (ȳ·n_eff, n_eff). The effective-sample-size (design-effect) correction for proportions from clustered samples follows [Korn & Graubard 1998](https://www150.statcan.gc.ca/n1/en/catalogue/12-001-X19980024356), who apply it to the Clopper–Pearson interval. This design applies it to Wilson so that the whole specification uses one interval family.
  3. The cap at n means epoch averaging never narrows the interval below the binary one.
  4. It never yields a zero-width interval. A normal interval would give [1, 1] for an all-correct clustered run and "pass" any band.
- **Decision p-value**: the Wilson closed form of `docs/design/audit-statistics.md` section 4.2, `z* = |ȳ − b| / sqrt(b(1 − b)/n_eff)`, `p = erfc(z*/√2)`.
- **Reported alongside**: `seIid`, `seCluster` (when applicable), `nEff`, `clusters`, and the tool's own SE for reconciliation.

Worked examples:

- `inspect/judged_qa_30.eval`, primary score `model_graded_qa`: n = 30, ȳ = 0.9. Wilson 95% interval [0.743789, 0.965400]. For the band {lower: 0.70}: z* = 0.2/sqrt(0.21/30) = 2.390457, p = 0.016827, outcome **pass**, provided the judge is validated (section 8.7).
- Clustered, synthetic (`expected.json` → `workedExamples.effectiveSampleSizeWilson`): 40 binary items in 4 clusters of 10 with cluster means 1, 1, 0.6 and 0.6. Here ȳ = 0.8, SE_iid = 0.064051, SE_cl = 0.115470 (design effect 3.25), n_eff = 12. Wilson on n_eff gives [0.517272, 0.937231], against [0.652427, 0.895000] if clustering were ignored. With C = 4 < 10, a real criterion would be gated; the case pins the arithmetic.
- `inspect/tiny_qa.eval` with `clusterKey: passage_id`: the four group means 1, 0.5, 0.5 and 0 fall into C = 3 clusters. SE_cl = 0.216506 against SE_iid = 0.204124.

### 8.4 Attack-success rate per technique

1. Attack items are reduced per group with the plan's reducer (default `any`: an attack counts as successful when any repeat succeeded, which equals garak's hit@k with k = generations).
2. A criterion of kind `genai_attack_success` has one **member per technique** (or per category, with `groupBy: "category"`). Member i has xᵢ successful attacks out of nᵢ scored attacks and a Wilson interval (on n_eff when `clusterKey` is set, as in section 8.3). Errors and unscored items are excluded and counted.
3. The criterion follows `docs/design/audit-statistics.md` section 4.3. It **passes** only if every member passes: the intersection–union test, no adjustment. It **fails** if any member fails at P = min(1, m · min p_fail): Bonferroni within the criterion. Members with nᵢ < `minimums.memberSize` are `insufficient_support` and block a pass. The total of scored attacks MUST reach `minimums.sampleSize`.
4. The headline is the worst member, the largest rate, with its interval bounds per section 4.7 of that design.
5. Overall attack-success rate across techniques is descriptive. Pooling techniques of different difficulty answers no audit question, so it is shown but never decides.

Worked examples (fixtures; Wilson 95%):

| Source | Technique | x/n | Interval |
|---|---|---|---|
| `promptfoo/redteam_shaped` | `excessive-agency` | 2/2 | [0.342380, 1] |
| | `harmful:hate` | 0/2 | [0, 0.657620] |
| | `hijacking`, `pii:direct` | 1/2 each | [0.094531, 0.905469] |
| | overall (descriptive) | 4/8 | [0.215216, 0.784784] |
| `garak/tiny.report` | `lmrc.Anthropomorphisation` × `lmrc.Anthro` (any of 2 generations) | 3/6 | [0.187616, 0.812384] |

At the Bonferroni level for m = 4 members (1 − 0.05/4 = 0.9875, z = 2.497705), `excessive-agency` 2/2 gives [0.242762, 1]. Every one of these criteria is gated: every member is below `memberSize` and every total is below `sampleSize`. They are format checks, not decisions.

### 8.5 Agents: pass^k and pass@k

For task t with nₜ trials (epochs) and cₜ successes, using τ-bench's unbiased estimators ([Yao et al. 2024](https://arxiv.org/abs/2406.12045), section 3) and pass@k from [Chen et al. 2021](https://arxiv.org/abs/2107.03374):

- `pass^k = mean_t [ C(cₜ, k) / C(nₜ, k) ]`: the probability that k independent trials **all** succeed.
- `pass@k = mean_t [ 1 − C(nₜ − cₜ, k) / C(nₜ, k) ]`: at least one succeeds. It is descriptive for assurance purposes, because reliability is about pass^k.

Rules:

- k ≥ 1, and every task needs nₜ ≥ k; tasks with fewer trials are `insufficient_support` (`below_k_trials`).
- The member value is the mean of task-level values vₜ ∈ [0, 1]. Its interval is Wilson on the effective sample size (section 8.3), with n = number of tasks. A criterion of kind `genai_pass_k` has one member per requested k.
- `pass^1 = pass@1 = mean(cₜ/nₜ)` (property test).

Worked example (`inspect/tiny_agent.eval`: c = 4, 2, 0 of n = 4): pass^1 = 0.5, pass^2 = (1 + 1/6 + 0)/3 = 0.388889, pass^3 = pass^4 = 0.333333, pass@2 = 0.611111.

### 8.6 Paired differences between models

A criterion of kind `genai_paired_difference` compares a candidate run with a baseline run on the same items. The two runs MUST have the same dataset fingerprint, or the comparison is restricted to the common `groupKey`s and the unmatched counts are reported.

- dᵢ = y_candidate,i − y_baseline,i over matched scored groups; estimate d̄.
- `SE_paired = sqrt( Σ (dᵢ − d̄)² / (n(n − 1)) )` (Miller 2024, eq. 7). With `clusterKey`, apply the clustered formula of section 8.3 to dᵢ (Miller eq. 8 with the C/(C − 1) correction).
- Interval: d̄ ± z·SE_paired, truncated to [−1, 1]. SE_paired = 0 gives `undefined` (`degenerate_interval`), which blocks a pass.
- Band: non-inferiority `{lower: −m}` (the candidate is at most m worse) or superiority `{lower: m}`. The decision p-value is the normal closed form `|d̄ − b| / SE`, as in `docs/design/audit-statistics.md` section 4.2. n MUST reach `minimums.sampleSize`.
- Reported alongside: the unpaired `SE = sqrt(SE_A² + SE_B²)` and Corr(y_A, y_B), so that the variance reduction from pairing is visible.

Worked example (n = 10, binary): A = 8/10, B = 5/10, d̄ = 0.3, SE_paired = 0.152753 (equal to the correlation form with Corr = 0.5), unpaired SE = 0.213437, 95% interval [0.000611, 0.599389]; the t-equivalent 1.963961 equals scipy's paired `ttest_rel` statistic. The example is gated at n = 10.

### 8.7 Judge validation, and why the judge must come from another family

**Why.** LLM judges show position bias, verbosity bias and **self-enhancement bias**, a preference for answers like their own ([Zheng et al. 2023](https://arxiv.org/abs/2306.05685)). Models can recognise their own generations, and that recognition causally drives a self-preference ([Panickssery et al. 2024](https://arxiv.org/abs/2404.13076)). A judge from the same family as the system under test shares training data and stylistic preferences with it, so its errors correlate with the system's and inflate scores. The judge must be independent of what it assesses, just as the auditor must be.

**Family.** A family is the developer-level model lineage: `openai`, `anthropic`, `google`, `meta`, `mistral`, `alibaba`, `deepseek`, `xai`, `cohere`, `microsoft`, `nvidia`, `ibm`, `amazon`, `ai21`, or `other-<name>`. Fine-tunes inherit the family of their base model, so a Llama fine-tune by any vendor is `meta`.

- Families are **declared** in the manifest for the system under test and for each judge.
- The engine computes a heuristic family from the model string with a prefix table in `engine/genai/families.py`, for example `gpt-`, `o1`, `o3` or `openai/` → `openai`; `claude` → `anthropic`; `gemini`, `gemma` or `google/` → `google`; `llama` or `meta-llama/` → `meta`; `mistral`, `mixtral` or `codestral` → `mistral`; `qwen` → `alibaba`; `deepseek` → `deepseek`; `grok` → `xai`; `command` or `cohere` → `cohere`; `phi-` → `microsoft`; `nemotron` → `nvidia`; `granite` → `ibm`; `nova` or `amazon.` → `amazon`.
- If declaration and heuristic disagree, the run gets `family_declaration_conflict`, and the judge is not validated until a reviewer acknowledges the conflict with a rationale (section 12.3).

**Kappa.** For the label file bound to judge J, with observed agreement p_o and chance agreement p_e = Σₖ p_{k·} p_{·k} from the marginals:

- `κ = (p_o − p_e)/(1 − p_e)` ([Cohen 1960](https://doi.org/10.1177/001316446002000104)).
- Large-sample variance ([Fleiss, Cohen & Everitt 1969](https://doi.org/10.1037/h0028106); the form [SAS PROC FREQ](https://documentation.sas.com/doc/en/pgmsascdc/9.4_3.5/procstat/procstat_freq_details78.htm) uses; identical to `statsmodels.stats.inter_rater.cohens_kappa`):

  ```text
  A = Σᵢ pᵢᵢ · [1 − (pᵢ· + p·ᵢ)(1 − κ)]²
  B = (1 − κ)² · Σ_{i≠j} pᵢⱼ · (p·ᵢ + pⱼ·)²
  C = [κ − p_e(1 − κ)]²
  Var(κ) = (A + B − C) / ((1 − p_e)² · n)
  ```

  Interval: κ ± z·sqrt(Var(κ)).
- p_e = 1 (a single label value) gives `kappa_undefined`, and the judge is not validated.

**A judge is validated** when all of the following hold:

1. Both families are declared and differ, and no family conflict is open.
2. The kappa was recomputed from a pinned label file bound to this judge's model and snapshot, so its validation level is L2.
3. n ≥ `judgeValidation.minimumItems` (50).
4. The kappa's 95% lower bound ≥ `minimumKappaLowerBound` (0.60, "substantial" agreement in [Landis & Koch 1977](https://doi.org/10.2307/2529310), applied to the lower bound rather than the point estimate).
5. For pairwise judges: the share of `pairId`s whose verdict mirrors when the order is swapped has a Wilson lower bound ≥ 0.80.

Worked examples:

| Label file | n | p_o | p_e | κ | SE | 95% interval | Validated |
|---|---|---|---|---|---|---|---|
| `judge_small_60.jsonl` | 60 | 0.85 | 0.54 | 0.673913 | 0.099650 | [0.478603, 0.869223] | no: the lower bound is below 0.60, although the point estimate is "substantial" |
| `judge_large_200.jsonl` | 200 | 0.915 | 0.521 | 0.822547 | 0.041137 | [0.741920, 0.903174] | yes |

Judge validation is a gate condition, not a criterion, so it is outside the Holm and BH families.

### 8.10 Reconciliation and claim scope

**Reconciliation.** Each tool aggregate the engine can recompute (sections 7.2–7.8) gets `{metric, tool, ours, absDiff, status}`, where status is `match` (|difference| ≤ `reconciliationTolerance`), `mismatch` or `not_comparable` (a different method, such as garak's bootstrap). Any `mismatch` adds `tool_aggregate_mismatch`. The engine's value stands; the gate requires an acknowledgement.

**Claim scope.** The engine generates, and #33 inserts into the working paper verbatim:

- **Mean score**: "{metric} {estimate} ({level}% interval {lower}–{upper}; n = {n} items of {dataset}@{version}) for {model snapshot}, with the recorded system prompt (SHA-256 {first 12 hex}), decoding settings and harness {harness}@{version}. This is accuracy on this benchmark, not accuracy on the population of real inputs (NIST AI 800-3)."
- **Attack success**: "Attack-success rate {estimate} ({interval}; n = {n}) for {technique} from {attackSet}@{version}, judged by {judge or detector}. It holds only for this attack set, this configuration and this judge; a low rate does not show that the system is secure against other attacks."
- **Judge**: "Judge {model} agreed with human labels with kappa {k} ({interval}; n = {n})."
- **Edited logs**: "{count} scores were edited after the run by {authors}; the reported figures use the {policy} scores."

### 10.2 Worker job `genai_ingest`

**Request.** The workspace freezes the request and the worker validates it:

```json
{"schemaVersion": "genai-1.0", "executionMode": "genai_ingest", "engagementId": "ENG-…", "jobId": "JOB-…",
 "procedure": {"id": "…", "revision": 3, "briefRevision": 2, "programRevision": 4},
 "inputs": [{"index": 0, "artifactId": "EV-…", "name": "judged_qa_30.eval", "sha256": "…", "size": 92626, "role": "log", "format": "inspect_eval"}],
 "manifest": {"schemaVersion": "genai-bundle/0.1", "…": "…"},
 "plan": {"schemaVersion": "genai-plan/0.1", "…": "…"},
 "inputHashes": {"0": "…"}}
```

**Python changes (#32).**

- `worker_contract.validate_request` dispatches on `schemaVersion`. `"1.0"` keeps today's path; `"genai-1.0"` goes to `validate_genai_request`, which checks:
  - at most 64 inputs, each no larger than `MAX_INPUT_FILE_BYTES` and together within `MAX_BUNDLE_BYTES`;
  - hex digests;
  - manifest inputs equal to request inputs;
  - plan and manifest valid.
- `Transport.input` gains the purpose `evidence` with an `index` parameter (`GET /api/runner?…&input=evidence&index=<i>`). Downloaded bytes MUST match `size` and `sha256`, and are written create-once as `inputs/genai-<index>.bin`. Names are never used as paths.
- `compute_job` dispatches to `engine.genai.ingest.run_bundle`. It runs in the existing `ProcessExecutor` (nothing executes models) or in `DockerExecutor`, under the same compute timeout (default 300 s, at most 600 s).
- `verify_result_bytes` gains `verify_genai_result_bytes`. It checks `schemaVersion`, `computationSha256 = sha256(computationJSON)`, the items hash, `provenance.requestSha256` and `provenance.inputHashes` equal to the request.
- The worker advertises the capability `genai_ingest` in its claim formats. Failure codes from section 11.6 are added to the `engine/WORKER.md` table (PR #47's mechanism).

**TypeScript changes (#33)**, in `site-app/app/api/runner/route.ts`, `site-app/lib/assurance-core.ts` and `site-app/app/api/assurance/route.ts`:

- Enrollment accepts the capability `genai_ingest`.
- The claim filter becomes `formats.includes(r.executionMode === 'auditor_model' ? r.model.format : r.executionMode === 'genai_ingest' ? 'genai_ingest' : 'provided_predictions')`.
- `GET` accepts `input=evidence&index=<i>` only for `genai_ingest` requests. It finds `r.inputs[i]`, re-checks the engagement artifact's SHA-256 against the pin, and streams the bytes.
- Completion parses the result with a discriminated union on `schemaVersion`: the existing `resultEnvelope` for `"1.0"`, and a new `genaiResultEnvelope` (section 10.3) whose pins are checked against the frozen request.
- `queueGenaiIngest` freezes the request in `execution_jobs`. That table is generic (request JSON plus hash), so no D1 migration is expected.

### 10.3 Result envelope (`genai-result/0.1`)

```json
{"schemaVersion": "genai-result/0.1",
 "computationJSON": "<canonical JSON string of the computation>",
 "computationSha256": "<sha256 of computationJSON, UTF-8>",
 "itemsJSONL": "<canonical JSONL string, items sorted by itemKey> | null",
 "itemsSha256": "<sha256 of the canonical JSONL, whether inline or not>",
 "provenance": {"channel": "runner | cli", "producedAt": "…", "requestSha256": "… | null",
                "inputHashes": {"0": "…"}, "workerVersion": "… | null", "imageDigest": "… | null",
                "executionMode": "genai_ingest"}}
```

- **Exact strings.** Hashed parts are carried as exact strings, following the existing `requestJSON` practice. TypeScript verifies SHA-256 over the string's UTF-8 bytes and then parses it, without re-serialising. Python writes `1.0` where JavaScript writes `1`, so a hash over re-serialised JSON would never match across the two languages.
- **`computation`** (`genai-computation/0.1`) contains:
  - `engine` (`version`, `genaiVersion`, parser versions, `statisticsVersion`, `taxonomyVersion`);
  - `plan` with `planSha256`, and `manifest` with `manifestSha256`: SHA-256 of `canonical_bytes` of the parsed objects, so that the CLI path (files) and the worker path (objects inside the request) give the same hash;
  - `inputs[]` (`name`, `sha256`, `bytes`, `format`, `formatVersion`, `role`);
  - `runs[]`, each with `runMetadata`, `statusCounts`, `postRunEdits`, `toolAggregates`, `reconciliation`, `items` (`count`, `sha256`, `inline`), `evidenceLevel`, `levelReasons`, `criteria` in the shape of `docs/design/audit-statistics.md` section 11, and `claimScope`;
  - `comparisons[]`, `judgeValidation[]`, and `warnings[]` as `{code, count, examples}`, where `examples` holds at most 20 locators.
- **Items** are inline when their canonical JSONL is at most 4 MiB. Otherwise `itemsJSONL` is null, and the full file is written next to the result (`--items-output`, or the worker job directory). The auditor MAY upload it as evidence; the workspace links it only if its SHA-256 equals `itemsSha256`.
- **Limits.** `computationJSON` at most 7 MiB, and the whole envelope within the existing 8 MiB result limit (`evidence_too_large`).

### 10.4 Workspace import

- **Worker path.** Covered by the runner changes in 10.2, then `compileGenaiResult` (12.1).
- **Upload path.** `importGenaiEnvelope {artifactId}` reads an accepted evidence artifact. It verifies both hashes, checks that every `computation.inputs[].sha256` equals an accepted artifact of the engagement, and records custody `uploaded` (effective level capped at L1, section 4.2).

### 10.5 Why not in the Cloudflare Worker

The hosted runner stays for tabular saved predictions. GenAI ingestion cannot run there:

- A Worker isolate has **128 MB** of memory and at most 5 minutes of CPU per request on the paid plan ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/)). A 50 MB log expands well beyond that once decompressed (Inspect entries decompress about 5:1) and parsed into objects.
- The Compression Streams standard defines brotli, deflate, deflate-raw and gzip, but **no zstd** ([WHATWG](https://compression.spec.whatwg.org/), updated 19 October 2026). Inspect logs need zstd.
- Re-runs (L3) need long-running, networked processes isolated from the platform. Those belong in the external worker (R6.4) or the client's environment (research synthesis, section 5.5).

### 10.6 L3 re-runs (shape fixed now, delivered by R6.4)

Until the worker can run harnesses itself, L3 comes from the auditor running the tool and then ingesting its logs through `genai_ingest`, with `origin: "auditor_rerun"` and a **`genai_rerun_attestation`** assurance record. The record holds:

- `bundleSha256s` (every input SHA-256);
- `harness {name, version, imageDigest?}`;
- `systemUnderTest {endpoint host only, snapshot}`;
- `runWindow {start, end}`;
- `environment` (free text up to 2,000 characters);
- `statement` ("I ran this evaluation as described; the pinned files are its unmodified output").

It is created by the Auditor or Lead Auditor who ran it and reviewed under the normal independent-review rules.

When signing keys exist (#25, R7.1 and R7.5), the same content becomes an in-toto Statement: `subject` holds the log digests; the predicate type is `https://in-toto.io/attestation/test-result/v0.1`, with `result` PASSED, WARNED or FAILED for an outcome of pass, inconclusive or fail; and `configuration` holds resource descriptors for the harness image, plan and dataset ([predicate](https://github.com/in-toto/attestation/blob/main/spec/predicates/test-result.md)). It is DSSE-signed and timestamped (R7.2).

## 11. Security

### 11.1 Threat model

Ingested files come from the auditee, or from tools the auditee configured, so treat them as hostile:

- crafted to crash or exhaust the parser (zip bombs, deep nesting, huge numbers);
- crafted to make it execute code (pickles, task files, `!function` hooks, JavaScript assertions, `trust_log`);
- crafted to escape paths (zip entry names);
- crafted to mislead reviewers (edited scores, forged tool hashes, prompt-injection text aimed at people or assistants, terminal escape sequences such as those garak's `ansiescape` probe produces, Unicode bidirectional controls);
- carrying secrets (provider keys in configuration, environment blocks, stack traces).

### 11.2 Parser rules (normative)

1. Parsers take **bytes**, never paths. They do no filesystem access, no network access and no subprocesses; tests patch `socket` and `subprocess` to raise.
2. No `pickle`, `marshal`, `shelve`, `yaml`, `ast.literal_eval`, `eval` or `exec`. No `importlib` or `__import__` driven by data, and no `re.compile` of input strings. Tests assert that `sys.modules` contains no tool package (`inspect_ai`, `lm_eval`, `garak`, `promptfoo`, `pyrit`, `deepeval`, `ragas`) after any parse.
3. JSON goes through `readers.load_json`: the stdlib decoder with `object_pairs_hook` rejecting duplicates, `parse_constant` mapping to `NonFinite`, and an iterative depth and size walk after decoding. Integers stay within Python's default 4,300-digit conversion limit (`sys.int_info.default_max_str_digits`); a longer integer is `invalid_json`. `RecursionError` becomes `nesting_too_deep`.
4. Zip: the central directory is parsed with stdlib `zipfile`. Every name in it is checked, and one unsafe name rejects the whole archive. Nothing is ever extracted to disk, so the check treats such a name as evidence of tampering rather than as a traversal risk. Only allowlisted entry names are read. The rules, each with the code it raises:
   - a safe name (no `..`, no absolute path, no backslash, no NUL, at most 512 bytes): `zip_entry_unsafe_name`;
   - no encryption flag: `zip_encrypted`;
   - a supported method: `zip_method_unsupported`;
   - a declared uncompressed size within the limits: `zip_entry_too_large`;
   - streamed decompression that stops at limit + 1 byte;
   - a ratio check for entries over 1 MiB: `zip_ratio_exceeded`;
   - a CRC-32 match: `zip_crc_mismatch`.

   Duplicate names are `zip_invalid`.
5. Text is never rendered. Excerpts and labels are inert strings. The workspace displays them with React text nodes only, never `dangerouslySetInnerHTML`, and shows C0/C1 control characters, bidirectional controls (U+202A–U+202E, U+2066–U+2069) and tag characters (U+E0000–U+E007F) as visible escapes. The CLI escapes them in its output.
6. Ingested text never reaches an LLM through this pipeline. If a future assistant (R-series) reads GenAI evidence, it must treat that text as untrusted data, as `engine/CITED_ASSISTANT.md` already requires.

### 11.3 Limits (`engine/genai/limits.py`)

| Constant | Value | Why |
|---|---|---|
| `MAX_INPUT_FILE_BYTES` | 50 MiB | The evidence upload limit (`site-app/app/api/evidence/route.ts`) |
| `MAX_BUNDLE_FILES` / `MAX_BUNDLE_BYTES` | 64 / 200 MiB | lm-evaluation-harness writes one samples file per task |
| `MAX_DECOMPRESSED_BYTES` / `MAX_ENTRY_BYTES` / `MAX_ZIP_ENTRIES` | 512 MiB / 128 MiB / 50,000 | Inspect logs. The observed ratio is about 5:1 |
| `MAX_ENTRY_RATIO` | 500:1, for entries over 1 MiB | Zip-bomb defence above any observed JSON ratio |
| `MAX_JSONL_LINE_BYTES` | 16 MiB | garak attempts with long outputs |
| `MAX_JSON_DEPTH` / `MAX_OBJECT_KEYS` / `MAX_STRING_BYTES` | 64 / 10,000 / 16 MiB | Inspect event nesting stays well under 64 |
| `MAX_ITEMS` | 100,000 per bundle | #32 MUST measure peak memory on a synthetic 100,000-item lm-evaluation-harness bundle. If tracemalloc peak exceeds 768 MiB, lower this to the largest power of ten that passes and record the measurement |
| `MAX_SCORES_PER_ITEM` / `MAX_LABELS` | 50 / 50 | Schema bounds |
| Inline items / computation / envelope | 4 MiB / 7 MiB / 8 MiB | Worker result limits |

### 11.4 Secrets and configuration

Metadata is extracted from allowlisted keys only (sections 7.2–7.8); configuration objects are never copied whole. Every extracted string is scanned for these patterns:

- `sk-[A-Za-z0-9_-]{16,}`
- `AKIA[0-9A-Z]{16}`
- `gh[pousr]_[A-Za-z0-9]{30,}`
- `xox[abprs]-[A-Za-z0-9-]{10,}`
- `AIza[0-9A-Za-z_-]{35}`
- `-----BEGIN [A-Z ]*PRIVATE KEY-----`
- URLs whose query contains `key=`, `token=` or `sig=`

A match is replaced by `[redacted:<first 12 hex of SHA-256>]` and counted in `secret_like_value_redacted`. The raw log stays internal in R2; the client projection of #33 never includes GenAI envelopes or items.

### 11.5 Fuzzing and property tests (`engine/tests/test_genai_fuzz.py`, `test_genai_properties.py`)

**Seeded mutation fuzzer, standard library only.** For each format, start from its fixtures and apply mutators:

- bytes: flip, insert, delete, truncate, duplicate a range;
- JSON structure: drop a key, duplicate a key, change a type, nest 10,000 levels, a 10⁶-digit integer, `1e999`, `NaN` in every number position, a lone surrogate `\ud800`, a BOM, invalid UTF-8, CRLF;
- JSONL: blank lines, a 17 MiB line, a non-object line;
- zip: a bad CRC, unsupported method 99, the encrypted flag, names with `../`, `C:\` or a NUL, duplicate names, local and central sizes that disagree, ZIP64 extra fields, and a zstd bomb of 1 GiB of zeros;
- format confusion: every parser on every other format's fixture.

The **oracles**:

1. Only `GenaiInputError` with an enumerated code escapes.
2. Any output validates against the schema.
3. Wall time per input up to 1 MiB stays under 2 s.
4. tracemalloc peak stays under 64 MiB for inputs up to 1 MiB.
5. No module from rule 2 is imported.
6. The same input gives the same output.

CI runs 300 iterations per format (`GENAI_FUZZ_ITERATIONS`, seed `GENAI_FUZZ_SEED`, default 31). A nightly or local run uses 20,000 iterations.

**Optional coverage-guided harness.** `engine/tests/fuzz/genai_atheris.py` uses [atheris](https://github.com/google/atheris) (Apache-2.0). It is never a runtime or CI dependency.

**Property tests:**

- singleton clusters give `SE_cl = SE_iid`;
- Wilson bounds lie in [0, 1] and contain the estimate;
- pass^1 = pass@1 = mean success;
- kappa is symmetric when the raters are swapped;
- permuting JSONL lines leaves aggregates unchanged (garak, lm-evaluation-harness, Ragas, PyRIT);
- `itemKey` values are unique;
- lm-evaluation-harness `prompt_hash` equals SHA-256 of `arg_0`;
- the redacted fixtures still parse.

**"Names code but runs nothing" test.** A generated Inspect log whose `eval.task_file`, scorer names and metric options name a module in a temp directory that would create a marker file on import. A generated lm-evaluation-harness results file with a `!function` source string. A promptfoo file with a `javascript` assertion and a `file://` provider. After ingestion: no marker exists, no new module is loaded, and the items are parsed.

## 14. Open questions and risks (each has a default)

| # | Question | Default |
|---|---|---|
| Q1 | The OWASP LLM Top 10 2026 identifiers come from CSA and other secondary summaries; the official PDF was not parsed | Use them as in 9.2; W3 MUST confirm against the official document before releasing the pack |
| Q2 | Should an uploaded envelope count as L2 when a reviewer re-performs it locally? | No. Only a worker recomputation authenticates it (4.2). Re-performance with `verify` is recorded but does not lift the cap |
| Q3 | κ ≥ 0.60 on the 95% lower bound with n ≥ 50: is it too strict for small validation budgets? | Keep it as a floor. Plans may raise it, never lower it. A methodology owner should sign this off |
| Q4 | Genuine `promptfoo redteam run` output was not generated (email verification) | Field names are verified from source at 0.125.1. Add a real red-team fixture when one is available, and re-check the `promptfoo:redteam:*` assertion names then |
| Q5 | PyRIT has no exporter; `pyrit-export/1` depends on PyRIT's pydantic model shapes | Gate on PyRIT major version 1; re-verify each minor release; switch to PyRIT's own `--output json` when it ships |
| Q6 | Family for distilled models, merges and models trained on another family's outputs | Developer-level base lineage; declare `other-<name>` with a rationale when unclear. A reviewer resolves conflicts |
| Q7 | The analytic clustered SE departs from `docs/design/audit-statistics.md` section 5.11 (cluster bootstrap for tabular data) | Keep the analytic CR1 form for GenAI means: it reconciles with Inspect and needs no seed. The bootstrap stays available as a cross-check |
| Q8 | Paired binary differences use a normal interval; a score interval for paired proportions (Newcombe 1998) would be better for small discordant counts | Normal interval with n ≥ 30; revisit with #21 |
| Q9 | Multi-gigabyte agent logs exceed the 50 MB upload and parse limits | Out of scope for 0.1. Needs chunked or streamed upload and an incremental parser |
| Q10 | DeepEval and Ragas carry no harness version or model identity, so their results rest on declarations | They are accepted, and the gate makes the declarations visible (`declaredOnly`). Recommend Inspect or promptfoo where the client can choose |
| Q11 | Inspect `.json` and `.eval` holding the same log have different bytes and hashes | Pin the file actually supplied. `inspect log convert` output is a different artifact |
| Q12 | Real logs can contain personal data or harmful text, which matters for excerpts and retention | Excerpts off by default. Envelopes are internal-only. Retention follows R7.4 |
